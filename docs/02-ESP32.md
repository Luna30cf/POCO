# POCO — Configuration et utilisation de l’ESP32

## 1. Objectif du document

Ce document centralise toutes les informations techniques concernant l’ESP32 utilisé dans le projet POCO.

Il présente notamment :

* le modèle de la carte ;
* son rôle dans le système ;
* son identification ;
* son alimentation ;
* l’intégration de l’interrupteur ON/OFF ;
* les GPIO utilisés ;
* les communications Wi-Fi et BLE ;
* le comportement prévu au démarrage ;
* les règles de sécurité liées aux capteurs et aux actionneurs.

Les informations détaillées concernant le câblage électrique seront regroupées dans :

```text
docs/08_Cablage.md
```

# 2. Carte utilisée

Le projet utilise une carte de développement ESP32 DevKit.

Les informations récupérées avec `esptool` sont les suivantes :

```text
Modèle de la puce : ESP32-D0WD-V3
```

```text
Adresse MAC : 1C:C3:AB:D2:A7:E4
```

Le firmware installé est :

```text
MicroPython v1.28.0
```

L’ESP32 intègre notamment :

* un processeur double cœur ;
* une connexion Wi-Fi 2,4 GHz ;
* du Bluetooth classique ;
* du Bluetooth Low Energy ;
* plusieurs entrées et sorties numériques ;
* des entrées analogiques ;
* des interfaces I2C, SPI et UART ;
* plusieurs modes de gestion énergétique.

---

# 3. Rôle de l’ESP32 dans POCO

L’ESP32 est le contrôleur principal du pot connecté.

Il assure les fonctions suivantes :

* lire l’humidité du sol ;
* mesurer la luminosité ambiante ;
* détecter le niveau d’eau du réservoir ;
* convertir les mesures dans un format exploitable ;
* gérer le premier appairage par Bluetooth Low Energy ;
* recevoir les identifiants Wi-Fi ;
* se connecter au réseau Wi-Fi ;
* publier les mesures par MQTT ;
* recevoir les commandes MQTT ;
* commander la pompe ;
* commander l’éclairage de croissance ;
* empêcher l’arrosage lorsque le réservoir est vide ;
* mémoriser sa configuration locale ;
* signaler son état de fonctionnement.

L’ESP32 ne gère pas directement :

* les comptes utilisateurs ;
* les droits d’accès ;
* l’historique complet des mesures ;
* la gestion détaillée des plantes ;
* l’affichage du dashboard.

Ces responsabilités sont attribuées au backend, à l’application web et à la base de données.

# 4. Identification du pot

Chaque pot POCO doit disposer d’un identifiant unique.

L’identifiant actuellement présent dans le topic MQTT :

```text
1hz3c6f7m9a
```

a été utilisé temporairement pendant les premiers tests.

Il ne correspond pas à un identifiant définitif et devra être remplacé.

## 4.1 Adresse MAC matérielle

L’adresse MAC relevée pour l’ESP32 est :

```text
1C:C3:AB:D2:A7:E4
```

Cette adresse est unique pour la carte.

Elle peut servir de base pour générer l’identifiant du pot.

Elle ne sera cependant pas forcément affichée directement à l’utilisateur.

---

## 4.2 Identifiant interne envisagé

L’identifiant interne peut être généré à partir de l’adresse MAC.

Plusieurs méthodes sont possibles :

* supprimer les deux-points ;
* utiliser uniquement une partie de la MAC ;
* inverser certains groupes ;
* ajouter un préfixe propre à POCO ;
* appliquer une fonction de génération déterministe.

Exemple à partir de la MAC :

```text
1C:C3:AB:D2:A7:E4
```

Version sans séparateur :

```text
1cc3abd2a7e4
```

Version raccourcie possible :

```text
d2a7e4
```

Version inversée possible :

```text
e4a7d2
```

Identifiant POCO possible :

```text
poco-e4a7d2
```

Pour le prototype, la convention retenue pourra être :

```text
poco-e4a7d2
```

Cet identifiant est :

* plus lisible que l’adresse MAC complète ;
* dérivé d’une donnée unique ;
* reproductible après une réinstallation ;
* suffisamment court pour être utilisé dans les topics MQTT.

La convention définitive devra être inscrite dans :

```text
docs/DECISIONS.md
```

---

## 4.3 Nom Bluetooth

Le nom diffusé en BLE pourra reprendre les derniers caractères de l’adresse MAC.

Exemple :

```text
POCO-A7E4
```

Ce nom permet à l’utilisateur de reconnaître physiquement le pot qu’il souhaite ajouter.

---

## 4.4 Identifiant en base de données

La base de données pourra contenir plusieurs identifiants distincts :

| Champ                 | Exemple                 | Rôle                          |
| --------------------- | ----------------------- | ----------------------------- |
| Identifiant technique | UUID généré par la base | Clé primaire                  |
| Identifiant du pot    | `poco-e4a7d2`           | Identification fonctionnelle  |
| Adresse MAC           | `1C:C3:AB:D2:A7:E4`     | Référence matérielle          |
| Nom BLE               | `POCO-A7E4`             | Recherche locale              |
| Nom utilisateur       | `Mon pothos`            | Nom choisi dans l’application |

Cette séparation évite d’utiliser l’adresse MAC comme seule clé métier.

# 5. Alimentation générale du prototype

Le prototype est alimenté en permanence par une alimentation USB-C 5 V.

L’ESP32 n’est pas directement alimenté en branchant un câble sur son propre connecteur USB.

L’entrée USB-C du pot utilise un module séparé :

```text
Connecteur USB 3.1 Type-C femelle
14 broches
traversant
PCB vertical
```

Ce module fournit le point d’entrée USB-C intégré dans le boîtier du pot.

L’alimentation reçue par le module doit ensuite être distribuée vers :

* l’ESP32 ;
* la pompe ;
* les circuits des LED ;
* les autres modules nécessitant du 5 V ou du 3,3 V.

Le câblage exact dépendra des tensions nécessaires à chaque composant.

---

# 6. Module USB-C utilisé

Le module prévu est un connecteur USB-C femelle monté sur une petite carte électronique.

Caractéristiques principales :

* prise USB Type-C femelle ;
* 14 broches ;
* montage traversant ;
* orientation verticale ;
* intégration possible dans une paroi du boîtier.

Ce module est utilisé comme entrée d’alimentation.

Le prototype n’utilise pas nécessairement les fonctions de transfert de données USB du connecteur.

L’objectif principal est de récupérer :

```text
5 V
```

et :

```text
GND
```

depuis une alimentation USB-C.

---

# 7. Vérification du module USB-C

Avant de raccorder l’ESP32 ou les actionneurs, le module USB-C devra être testé au multimètre.

Les vérifications à effectuer sont :

1. identifier les broches 5 V ;
2. identifier les broches GND ;
3. brancher une alimentation USB-C ;
4. vérifier la présence d’environ 5 V ;
5. vérifier l’absence de court-circuit ;
6. confirmer la polarité ;
7. vérifier que le câble et l’alimentation fournissent suffisamment de courant.

Il ne faut pas raccorder directement tous les composants avant d’avoir validé la sortie du module.

---

# 8. Interrupteur général ON/OFF

Le prototype comportera un interrupteur physique permettant de couper entièrement son alimentation.

Le comportement attendu est :

```text
Interrupteur ON
        ↓
Alimentation du système
        ↓
Démarrage de l’ESP32
        ↓
Fonctionnement de POCO
```

et :

```text
Interrupteur OFF
        ↓
Coupure de l’alimentation
        ↓
Arrêt complet de POCO
```

Contrairement au deep sleep, l’interrupteur coupe réellement l’alimentation du système.

Lorsque l’interrupteur est sur OFF :

* l’ESP32 est éteint ;
* le Wi-Fi est coupé ;
* le BLE est coupé ;
* MQTT est déconnecté ;
* les capteurs sont éteints ;
* la pompe ne peut pas fonctionner ;
* les LED sont éteintes ;
* la consommation du système devient nulle ou négligeable selon le montage.

---

# 9. Emplacement de l’interrupteur

L’interrupteur doit être placé sur la ligne d’alimentation principale.

Architecture de principe :

```text
Alimentation USB-C
        │
        ▼
Module USB-C femelle
        │
        ▼
Interrupteur ON/OFF
        │
        ▼
Distribution de l’alimentation
        │
        ├── ESP32
        ├── Pompe
        ├── LED
        └── Capteurs
```

Cette architecture permet d’éteindre l’ensemble du pot avec un seul interrupteur.

Une autre possibilité serait de couper uniquement l’alimentation de l’ESP32, mais cette solution pourrait laisser certains circuits alimentés.

Pour le prototype, il est préférable que l’interrupteur coupe l’alimentation générale.

---

# 10. Choix de l’interrupteur

L’interrupteur devra être compatible avec :

* une tension d’au moins 5 V ;
* le courant maximal consommé par l’ensemble du prototype ;
* un montage dans le boîtier ;
* une manipulation fréquente ;
* un repérage clair des positions ON et OFF.

Types possibles :

* interrupteur à glissière ;
* interrupteur à bascule ;
* interrupteur à levier ;
* bouton poussoir à verrouillage ;
* interrupteur rotatif.

Un simple bouton poussoir momentané ne convient pas directement s’il ne conserve pas son état.

L’interrupteur choisi devra rester mécaniquement :

```text
ON
```

ou :

```text
OFF
```

après action de l’utilisateur.

---

# 11. Intensité admissible de l’interrupteur

L’interrupteur ne doit pas être sélectionné uniquement selon sa taille.

Il doit supporter le courant de l’ensemble du système.

La consommation totale comprend notamment :

* l’ESP32 ;
* la pompe ;
* les LED de croissance ;
* les capteurs ;
* les pertes liées aux circuits de puissance.

La pompe et les LED consommeront probablement beaucoup plus de courant que l’ESP32.

L’interrupteur devra donc être dimensionné pour la consommation maximale simultanée.

Une marge de sécurité devra être conservée.

Par exemple, si le système peut consommer environ 1 A, il est préférable d’utiliser un interrupteur prévu pour un courant supérieur.

La valeur exacte sera déterminée après mesure ou estimation complète de la consommation.

---

# 12. Absence de deep sleep dans le prototype

Le deep sleep n’est pas retenu pour le fonctionnement principal du prototype.

Cette décision repose sur plusieurs éléments :

* POCO est alimenté en permanence en USB-C ;
* le pot doit rester joignable en Wi-Fi ;
* MQTT doit pouvoir recevoir des commandes ;
* une commande d’arrosage doit pouvoir être reçue à distance ;
* le deep sleep coupe la connexion réseau ;
* le réveil demanderait une action physique ou une temporisation ;
* l’interrupteur permet déjà une extinction complète.

Le deep sleep sera donc documenté comme une solution étudiée mais non retenue.

Cette décision sera enregistrée dans :

```text
docs/DECISIONS.md
```

Il pourra être réévalué pour une future version sur batterie.

---

# 13. Broches d’alimentation de l’ESP32

Les broches d’alimentation principales sont :

| Broche        | Fonction                        |
| ------------- | ------------------------------- |
| `VIN` ou `5V` | Alimentation de la carte en 5 V |
| `3V3`         | Sortie régulée en 3,3 V         |
| `GND`         | Masse commune                   |

L’appellation exacte peut varier selon le modèle de la carte DevKit.

Avant le branchement définitif, il faudra vérifier les inscriptions présentes sur la carte.

---

# 14. Logique électrique de l’ESP32

Les GPIO de l’ESP32 fonctionnent en logique :

```text
3,3 V
```

Ils ne doivent pas recevoir directement un signal de 5 V.

Une tension trop élevée sur un GPIO peut endommager la carte.

Cette règle concerne notamment :

* les sorties de capteurs ;
* les modules alimentés en 5 V ;
* les signaux de commande ;
* les interfaces de communication.

Si un module fournit un signal de 5 V, une adaptation de niveau peut être nécessaire.

---

# 15. Masse commune

Tous les composants doivent partager une masse commune.

Cela concerne :

* l’ESP32 ;
* le module USB-C ;
* le capteur d’humidité ;
* le BH1750 ;
* le flotteur ;
* la pompe ;
* les MOSFET ;
* les LED ;
* les alimentations associées.

Schéma de principe :

```text
GND module USB-C
        │
        ├── GND ESP32
        ├── GND capteur d’humidité
        ├── GND BH1750
        ├── GND flotteur
        ├── GND circuit pompe
        └── GND circuit LED
```

Sans masse commune, les signaux de commande peuvent être instables ou inutilisables.

# 17. GPIO34 — Capteur d’humidité

Le capteur capacitif d’humidité du sol v1.2 est connecté au GPIO34.

Branchement envisagé :

| Capteur | ESP32  |
| ------- | ------ |
| VCC     | 3V3    |
| GND     | GND    |
| AO      | GPIO34 |

Initialisation :

```python
from machine import ADC, Pin

soil_adc = ADC(Pin(34))
```

Lecture :

```python
raw_value = soil_adc.read_u16()
```

Le GPIO34 est une entrée uniquement.

Il convient donc à la lecture analogique du capteur.

Il ne peut pas être utilisé pour commander :

* une pompe ;
* une LED ;
* un MOSFET ;
* une sortie numérique.

---

# 18. Conversion analogique

La fonction utilisée est :

```python
soil_adc.read_u16()
```

Elle retourne une valeur comprise approximativement entre :

```text
0
```

et :

```text
65535
```

La mesure dépend notamment :

* de l’alimentation du capteur ;
* du type de terre ;
* de l’humidité réelle ;
* de la profondeur d’insertion ;
* du vieillissement du capteur ;
* du bruit électrique.

Les valeurs doivent donc être calibrées.

---

# 19. Calibration actuelle du capteur d’humidité

Les valeurs actuellement retenues sont :

```python
SOIL_DRY = 28000
SOIL_WET = 17000
```

La conversion utilisée est :

```python
percent = 100 * (value - SOIL_DRY) / (SOIL_WET - SOIL_DRY)
percent = max(0, min(100, percent))
```

Cette formule permet d’obtenir un pourcentage compris entre :

```text
0 %
```

et :

```text
100 %
```

Le détail des mesures et des tests sera placé dans :

```text
docs/03_Capteur_Humidite.md
```

# 20. GPIO21 et GPIO22 — BH1750

Le capteur de luminosité BH1750 communique en I2C.

Broches prévues :

| Signal |   GPIO |
| ------ | -----: |
| SDA    | GPIO21 |
| SCL    | GPIO22 |

Initialisation :

```python
from machine import I2C, Pin

i2c = I2C(
    0,
    sda=Pin(21),
    scl=Pin(22),
    freq=400000
)
```

Test de détection :

```python
print(i2c.scan())
```

Le BH1750 utilise généralement l’adresse :

```text
0x23
```

ou :

```text
0x5C
```

L’adresse réelle devra être confirmée par le scan.

---

# 21. GPIO27 — Flotteur du réservoir

Le flotteur fonctionne comme un contact mécanique.

Il peut présenter deux états :

```text
contact ouvert
```

ou :

```text
contact fermé
```

Le GPIO27 est envisagé pour sa lecture.

Exemple :

```python
from machine import Pin

water_level = Pin(
    27,
    Pin.IN,
    Pin.PULL_UP
)
```

Lecture :

```python
state = water_level.value()
```

La signification de `0` et `1` devra être testée physiquement.

Le système devra déterminer si le flotteur est configuré comme :

* normalement ouvert ;
* normalement fermé.

La logique ne devra pas être considérée comme définitive avant le test réel.

---

# 22. GPIO25 — Commande de la pompe

La pompe ne doit jamais être branchée directement sur un GPIO.

Le GPIO25 commandera uniquement un étage de puissance.

Architecture de principe :

```text
GPIO25
   │
   ▼
Résistance de grille
   │
   ▼
MOSFET
   │
   ▼
Pompe 5 V
```

Initialisation :

```python
from machine import Pin

pump = Pin(25, Pin.OUT, value=0)
```

Activation :

```python
pump.value(1)
```

Arrêt :

```python
pump.value(0)
```

---

# 23. Sécurité de la pompe

La pompe devra être arrêtée par défaut.

Les protections logicielles prévues sont :

* arrêt immédiat au démarrage ;
* durée maximale d’activation ;
* arrêt automatique après arrosage ;
* interdiction d’arroser si le réservoir est vide ;
* délai minimal entre deux arrosages ;
* arrêt en cas d’erreur ;
* rejet des commandes invalides.

Exemple conceptuel :

```python
if reservoir_is_empty():
    pump.value(0)
else:
    activate_pump_for(max_duration_ms=3000)
```

La durée définitive devra être déterminée par des tests.

---

# 24. Protection électrique de la pompe

La pompe étant une charge inductive, une diode de roue libre doit être prévue.

Elle permet de limiter la surtension produite lorsque la pompe est arrêtée.

Le montage doit comprendre au minimum :

* la pompe ;
* un MOSFET adapté ;
* une résistance de grille ;
* une résistance pull-down ;
* une diode de roue libre ;
* une alimentation adaptée ;
* une masse commune avec l’ESP32.

Le schéma détaillé sera placé dans :

```text
docs/08_Cablage.md
```

# 25. GPIO26 — Commande des LED

Le GPIO26 est envisagé pour commander les LED de croissance.

Les LED de puissance ne doivent pas être alimentées directement par l’ESP32.

Le GPIO26 devra commander :

* un MOSFET ;
* un driver ;
* ou un autre circuit de puissance adapté.

Initialisation simple :

```python
from machine import Pin

grow_light = Pin(26, Pin.OUT, value=0)
```

Activation :

```python
grow_light.value(1)
```

Arrêt :

```python
grow_light.value(0)
```

---

# 26. Utilisation éventuelle du PWM

Une variation de la puissance lumineuse pourra être envisagée avec le PWM.

Exemple :

```python
from machine import PWM, Pin

grow_light_pwm = PWM(
    Pin(26),
    freq=1000,
    duty_u16=0
)
```

Le circuit des LED devra être compatible avec ce type de commande.

Pour le premier prototype, un fonctionnement simple ON/OFF pourra être privilégié afin de limiter la complexité.

---

# 27. Broches à éviter

Les GPIO suivants sont généralement reliés à la mémoire flash :

```text
GPIO6 à GPIO11
```

Ils ne doivent pas être utilisés.

Leur utilisation peut empêcher l’ESP32 de démarrer.

---

# 28. Broches de démarrage

Certaines broches influencent le démarrage de l’ESP32.

Elles comprennent notamment :

```text
GPIO0
GPIO2
GPIO5
GPIO12
GPIO15
```

Il faut éviter qu’un composant leur impose un niveau logique incorrect lors de la mise sous tension.

Pour cette raison, les actionneurs principaux sont attribués à d’autres GPIO.

---

# 29. GPIO uniquement utilisables en entrée

Les broches suivantes sont généralement utilisables uniquement en entrée :

```text
GPIO34
GPIO35
GPIO36
GPIO39
```

Elles peuvent servir pour :

* des signaux analogiques ;
* des capteurs ;
* des contacts numériques.

Elles ne peuvent pas commander un actionneur.

---

# 30. Initialisation sécurisée

Les sorties commandant la pompe et les LED doivent être initialisées immédiatement à l’état inactif.

Exemple :

```python
from machine import Pin

pump = Pin(25, Pin.OUT, value=0)
grow_light = Pin(26, Pin.OUT, value=0)
```

Cette étape doit être exécutée avant :

* la connexion Wi-Fi ;
* le lancement du BLE ;
* la connexion MQTT ;
* la lecture des capteurs ;
* le traitement des commandes.

L’objectif est d’éviter une activation accidentelle au démarrage.

---

# 31. Wi-Fi

Le Wi-Fi est utilisé pour le fonctionnement quotidien du pot.

L’ESP32 fonctionne en mode station :

```python
network.STA_IF
```

Exemple :

```python
import network

wlan = network.WLAN(network.STA_IF)
wlan.active(True)
```

L’ESP32 doit être connecté à un réseau :

```text
Wi-Fi 2,4 GHz
```

Un réseau exclusivement 5 GHz n’est pas compatible avec l’ESP32 classique utilisé.

---

# 32. Bluetooth Low Energy

Le BLE est utilisé pour la configuration initiale.

L’application devra pouvoir :

* rechercher les pots POCO ;
* afficher le nom BLE ;
* se connecter au pot ;
* lire son identifiant ;
* transmettre le SSID du Wi-Fi ;
* transmettre le mot de passe Wi-Fi ;
* transmettre un jeton d’association ;
* recevoir l’état de la connexion ;
* confirmer l’ajout du pot.

Nom BLE envisagé :

```text
POCO-A7E4
```

---

# 33. Activation du mode BLE

Le mode d’appairage BLE devra être actif lorsque :

* le pot démarre pour la première fois ;
* aucune configuration Wi-Fi n’est enregistrée ;
* la connexion Wi-Fi échoue durablement ;
* la configuration locale a été supprimée ;
* l’utilisateur lance une procédure de réinitialisation.

Une fois le Wi-Fi configuré, le BLE pourra être désactivé.

Il n’a pas besoin de rester actif pendant le fonctionnement normal.

---

# 34. Service BLE de provisioning

Le service BLE pourra contenir plusieurs caractéristiques.

| Caractéristique      | Fonction                         |

# 35. Stockage local

L’ESP32 devra mémoriser une configuration minimale.

Exemple conceptuel :

```json
{
  "wifi_ssid": "NomDuReseau",
  "wifi_password": "MotDePasse",
  "device_id": "poco-e4a7d2",
  "paired": true
```

Pour le prototype, ce stockage pourra être réalisé dans un fichier JSON local.

Cette solution n’offre pas une protection forte des secrets.

Les données ne devront jamais être :

* publiées sur MQTT ;
* affichées dans les logs ;
* enregistrées dans Git ;
* envoyées sans contrôle à l’application web.

# 36. Comportement au démarrage

Lorsque l’interrupteur est placé sur ON, l’ESP32 démarre.

Le comportement prévu est le suivant :

```text
Interrupteur ON
      │
      ▼
Alimentation de l’ESP32
      │
      ▼
Initialisation de la pompe à OFF
      │
      ▼
Initialisation des LED à OFF
      │
      ▼
Chargement de la configuration
      │
      ├── Configuration absente
      │          │
      │          ▼
      │   Activation du BLE
      │
      └── Configuration présente
                 │
                 ▼
       Tentative de connexion Wi-Fi
                 │
                 ├── Connexion réussie
                 │          │
                 │          ▼
                 │   Connexion MQTT
                 │
                 └── Échec prolongé
                            │
                            ▼
                  Réactivation du BLE
```

---

# 37. Fonctionnement normal

Après la connexion :

```text
Lecture des capteurs
        │
        ▼
Création des messages JSON
        │
        ▼
Publication MQTT
        │
        ▼
Réception des commandes
        │
        ▼
Commande éventuelle des actionneurs
        │
        ▼
Nouvelle boucle
```

L’ESP32 reste allumé et connecté tant que l’interrupteur est sur ON.

---

# 38. Extinction du pot

Lorsque l’interrupteur est placé sur OFF :

```text
Interrupteur OFF
        │
        ▼
Coupure de l’alimentation
        │
        ▼
Arrêt immédiat de l’ESP32
```

Le système ne peut alors plus :

* publier de mesures ;
* recevoir de commandes ;
* être détecté en BLE ;
* piloter la pompe ;
* piloter les LED.

L’application devra considérer le pot comme hors ligne après une période sans message MQTT.

---

# 39. Conséquence d’une extinction pendant un arrosage

Si l’utilisateur éteint le pot pendant que la pompe fonctionne, la coupure générale d’alimentation arrête également la pompe.

Cette caractéristique est utile pour la sécurité.

Cependant, la base de données peut ne pas recevoir la confirmation de fin de l’arrosage.

Le backend devra donc éviter de considérer qu’une commande reste active indéfiniment.

Les commandes devront comporter :

* une durée ;
* un horodatage ;
* un identifiant ;
* un état d’exécution ;
* une expiration.

```python
def build_device_id(mac_address):
```

# 42. Topics MQTT envisagés

L’identifiant temporaire actuellement utilisé devra être remplacé par l’identifiant définitif.

Ancien exemple temporaire :

```text
poco/1hz3c6f7m9a/soil_sensor
```

Exemple avec l’identifiant dérivé de la MAC :

```text
poco/poco-e4a7d2/sensors/soil
```

Convention envisagée :

```text
poco/{device_id}/sensors/soil
poco/{device_id}/sensors/light
poco/{device_id}/sensors/water
poco/{device_id}/status
poco/{device_id}/commands/pump
poco/{device_id}/commands/light
```

Il pourra être décidé de ne pas répéter le préfixe `poco` dans l’identifiant.

Dans ce cas :

```text
device_id = e4a7d2
```

et :

```text
poco/e4a7d2/sensors/soil
```

Cette deuxième forme est plus courte et évite :

```text
poco/poco-e4a7d2/
```

La convention finale sera précisée dans `DECISIONS.md`.

# 43. Statut MQTT

Le pot pourra publier régulièrement son état.

Topic :

```text
poco/e4a7d2/status
```

Exemple :

```json
{
  "device_id": "e4a7d2",
  "online": true,
  "wifi_connected": true,
  "mqtt_connected": true,
  "mode": "normal"
}
```

Modes possibles :

```text
pairing
connecting
normal
watering
lighting
error
```

Le mode `sleeping` n’est pas retenu pour le prototype actuel.

# 44. Gestion des erreurs

L’ESP32 devra gérer au minimum :

* l’absence de configuration Wi-Fi ;
* un mauvais mot de passe Wi-Fi ;
* un réseau indisponible ;
* un broker MQTT inaccessible ;
* une perte de connexion ;
* un capteur non détecté ;
* une mesure incohérente ;
* un réservoir vide ;
* une commande invalide ;
* une pompe active trop longtemps ;
* un fichier de configuration corrompu.

Lorsqu’une erreur survient, le système devra :

1. placer les actionneurs dans un état sûr ;
2. tenter une reprise limitée ;
3. afficher l’erreur dans le REPL ;
4. publier l’erreur si MQTT est disponible ;
5. réactiver le BLE si la configuration réseau est inutilisable.

---

# 45. Watchdog

Un watchdog pourra être ajouté en fin de développement.

Son rôle est de redémarrer automatiquement l’ESP32 si le programme reste bloqué.

Exemple :

```python
from machine import WDT

wdt = WDT(timeout=10000)
```

Dans la boucle principale :

```python
wdt.feed()
```

Le watchdog n’est pas encore activé pendant la phase de développement, car il pourrait compliquer le débogage.

Il sera évalué lorsque :

* les capteurs seront intégrés ;
* MQTT sera stable ;
* le BLE sera stable ;
* les actionneurs seront sécurisés ;
* la boucle principale sera finalisée.

---

# 46. Protection contre l’eau

L’ESP32 et les circuits électroniques doivent être séparés :

* du réservoir ;
* de la terre humide ;
* du tuyau ;
* de la sortie de pompe ;
* des zones exposées aux éclaboussures.

Le boîtier devra prévoir :

* un compartiment électronique distinct ;
* une fixation de l’ESP32 ;
* des câbles maintenus ;
* des connexions isolées ;
* une entrée USB-C accessible ;
* un interrupteur accessible ;
* une ventilation minimale ;
* une séparation entre eau et alimentation.

Le prototype n’est pas considéré comme étanche.

---

# 47. Accessibilité des commandes physiques

Le boîtier devra permettre d’accéder à :

* l’interrupteur ON/OFF ;
* la prise USB-C ;
* le bouton BOOT de l’ESP32 si nécessaire ;
* le bouton RESET de l’ESP32 si nécessaire.

L’ESP32 pourra éventuellement être monté de manière à permettre son retrait pendant les phases de développement.

Dans la version finale, seuls l’interrupteur et la prise USB-C devront normalement être accessibles à l’utilisateur.
